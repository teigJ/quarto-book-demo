Handwritten Code: Translation and Execution

Execution Environment

  • I have detailed some of the handwriting translation techiniques already
  • So I’ll start by explaining the execution environment that I build for the C++ code

Podman container setup

Podman is a rootless container alternative to Docker, and has nearly one-to-one support for Docker images.

For my image, I landed on an Alpine-based build for its small size, I install the g++ compiler and coreutils inside it for its timeout utility.

I also point to an entrypoint script - run.sh - that dictates how the C++ file is compiled and where stdout and stdin are directed.

Podman Run Options

podman run --rm \
--network none \
--read-only \
--read-only-tmpfs=false \
--tmpfs /tmp:size=50m \
--memory 256m \
--memory-swap 256m \
--cpus 0.5 \
--pids-limit 64 \
--timeout 60 \
--cap-drop ALL \
--user sandbox \
--security-opt no-new-privileges \
-v ./hello.cpp:/sandbox/source.cpp:ro \
sandbox:cpp

The command is very large, so I’ll break it down flag by flag

  • --rm: deletes the container after it is done running
  • --network none: disables all network functionality
  • --read-only: makes the file system read-only
  • --read-only-tmpfs=false: makes the temporary file system not read-only
  • --tmpfs /tmp:size=50m: mounts the temporary file system with a 50 mb size restriction
  • --memory 256m: restricts RAM usage to 256mb
  • --memory-swap 256m: sets the swap to the same as the restriction, effectively disabling memory swap.
  • --cpus 0.5: throttles the container to only use up to half a CPU
  • --timeout 60: makes the container close itself after 60 seconds
  • --cap-drop ALL: removes all Linux kernel capabilities and priviledges
  • --user sandbox: assigns the sandbox user created during image generation
  • -v ./hello.cpp:/sandbox/source.cpp:ro:
    • ./hello.cpp is the example for the C++ file that is to be executed
    • /sandbox/source.cpp copies and mounts the file with a consistent filename in the given location
    • ro makes it read only.
  • sandbox:cpp is the image name

There may be additional options that make it more secure, but this is what I decided to go with for now, and what I ran all my tests with.

Manual Container Testing

I wrote some tests that would require the podman container to stop them, and I will include more details of the results of the full pipeline using the handwritten versions later.

For now, I will say that I tested the memory limit, network connection, pid limit, read-only file system (outside of tmp), and compilation failure.

After some debugging of my run.sh script, it was handling everything properly as far as I could tell from my tests.

Container Controller

When doing the testing manually, I had very limited information and my control and sight over stdout and stderr was limited.

There also were several manual steps to execution, like making the cpp file readable.

To solve this, I made a controller that formatted the stdout and stderr, and handled the file readability

Putting the Pieces Together

I now have a simple Python controller script that I can pass in a cpp file and it will compile and execute in a podman container and give me an output.

I also have ollama with a “custom” gemma4 model that will directly output a cpp file when I feed it an image and pipe its output into said file.

All I needed to do was put the two pieces together, and I would have a “image of handwritten code to code execution results” pipeline.

My Pipeline Script

First, I learned how to use ollama through its API to prompt the local model from inside a Python script. I also had to convert the prompt (and image using base64) into a json payload.

I store the returned code and harvest and print some statistics that the API returns.
Now that I have the code, I simply use the same function that I built earlier to run it inside a podman container and get the output.

I use my pipeline.py script to print things out and format them, but the assembly of all these components together really was that simple once I worked out some bugs.

#include <bits/stdc++.h>
using namespace std;

bool binarySearch(vector<int>& v, int low, int high, int target) {
    if (low > high) {
        return false;
    }
    int mid = ((high - low) / 2) + low;
    if (v[mid] == target) {
        return true;
    }
    if (v[mid] > target) {
        return binarySearch(v, low, mid - 1, target);
    }
    return binarySearch(v, mid + 1, high, target);
}

int main() {
    vector<int> v = {1, 2, 3, 4, 5, 8, 9, 11};
    int target = 8;
    if (binarySearch(v, 0, v.size() - 1, target)) {
        cout << target << " found.";
    } else {
        cout << target << " Not found.";
    }
    return 0;
}

Test Results

Here, I’m going to include the results of all the tests for code-reader (gemma4:26b with Modelfile baked in) and code-reader-qwen9b (qwen3.5:9b with Modelfile baked in)

My summary is that qwen outperformed gemma in accuracy and speed by a significant margin based upon these tests, and it is also less expensive in every way.

The tests with code-reader were done before I was harvesting and printing the statistics, but pretty much every test was slower, and in some cases less accurate, with the larger model.
