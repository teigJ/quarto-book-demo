Full App Migration

I have migrated the demo into a much more robust Flask app, and it now supports several more features.

  • Session
    • A user has a session that keeps track of all the submissions (the timestamp, image, code results, etc.)
  • Session History
    • This is where the user can view all the information tracked by the current session in a summary screen
    • Includes an easy-to-read PDF export
  • Sessions History (history of all sessions)
    • A history of the current and past sessions, so progress isn’t accidentally lost
  • New Session
    • A user can start a new session anytime they choose
    • Once a session is ended, it is considered “archived” and cannot be changed

User sessions are built using a UUID system, so there is no login/logout or user state. The user’s session UUIDs are stored for 30 days in their cookies locally, and the site generates based upon that, using the information stored in the DB (and the images stored on the disk)

Full Pipeline load testing

I made a load_test.py script that allows for testing the full pipeline with concurrent requests.

I ran 5 consecutive load tests, each with 10 users and a different image each to go through the whole process each time.

Below are two different figures that I made based on the results of those tests.

The first shows the increasing wait time for each user, and the second shows the variance accounting for the increasing queue time.

Code 
library(ggplot2)

times <- c(16.27, 18.28, 20.65, 22.92, 25.32, 27.47, 29.69, 32.43, 35.17, 37.53,
           17.85, 19.52, 21.31, 22.99, 24.80, 26.73, 28.46, 30.29, 32.15, 34.04,
           12.61, 14.14, 15.71, 17.51, 19.11, 20.73, 22.25, 24.02, 25.47, 27.35,
            9.62, 12.79, 16.02, 19.05, 22.72, 25.45, 28.85, 31.67, 35.50, 38.88,
            4.89,  6.65,  8.44, 10.20, 12.00, 13.78, 15.49, 17.29, 19.03, 20.86)

df <- data.frame(
  time = times,
  run = factor(rep(1:5, each = 10)),
  user_position = rep(1:10, times = 5)
)

ggplot(df, aes(x = user_position, y = time, color = run)) +
  geom_line(linewidth = 0.8) +
  geom_point(size = 2) +
  scale_x_continuous(breaks = 1:10) +
  labs(title = "Pipeline Completion Steadily Increases",
       x = "User position (order of finish)",
       y = "Elapsed time since test start (seconds)",
       color = "Run") +
  theme_minimal(base_size = 13)
  • Completion time increases steadily with each additional consecutive user in every run
    • This is consistent with a single-threaded bottleneck (the local LLM OCR process) queueing requests.
  • Run 5 starts fastest and stays lowest throughout, while Runs 1–4 cluster closer together
    • This matches my manual use of the LLM for OCR, occasionally it gets hung up or processes very quickly.
    • This variance has occured with the same image being translated over and over, so I don’t believe it likely that it differs entirely based on input.
Code 
library(dplyr)

deltas <- df %>%
  group_by(run) %>%
  arrange(user_position) %>%
  mutate(delta = time - lag(time)) %>%
  filter(!is.na(delta))

ggplot(deltas, aes(x = user_position, y = delta, color = run)) +
  geom_line(linewidth = 0.8) +
  geom_point(size = 2) +
  scale_x_continuous(breaks = 2:10) +
  labs(title = "OCR Bottleneck Adds ~2 Seconds per Additional User",
       x = "Nth consecutive user",
       y = "Added time vs. previous user (seconds)",
       color = "Run") +
  theme_minimal(base_size = 13)
  • Most runs add a fairly consistent ~1–2 seconds per additional consecutive user
    • gives a reasonable estimate of the actual per-request cost of the local LLM doing OCR under load.
  • Run 4 stands out with a higher (~3–3.8s) and less consistent cost, indicating the bottleneck isn’t always stable.
    • It may be worth investigating what factors contributed to this inconsistency, and if the LLM can be made to return more quickly and consistently under different parameters
